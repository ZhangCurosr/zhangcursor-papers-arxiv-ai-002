# 论文速读：The Unreliable Progress Bar: Can LLM Agents Reliably Report Task Progress Throughout Execution?

## 一句话总结
本文系统评估了LLM Agent在执行任务全生命周期中可靠报告进度的能力，发现几乎所有被测试模型在某些阶段可靠而在其他阶段不可靠，尤其在中途执行阶段普遍出现准确性大幅下降（"lost-mid-task pattern"），表明Agent框架不应仅依赖模型自身生成的进度信号控制任务流程。

## 研究问题与动机
1. **核心问题**：大语言模型能否在任务的每一个阶段可靠地报告任务进度（lifecycle stage）？如果不可靠，报告在何处、以何种形式失效？
2. **现有方法不足**：当前Agent框架（如LangChain、OpenAI Agents SDK等）大多将continue-or-stop决策权委托给模型生成的信号，但缺乏对模型进度报告可靠性的系统性度量——现有基准仅评估Agent"做了什么"（任务最终结果），不评估模型"告诉运行时任务进行到哪了"。
3. **实际风险**：如图1所示，当测量速度27.5 Mbps低于要求200 Mbps时，模型错误声明任务完成导致运行时无条件停止，而目标远未完成。
4. **研究空白**：经结构化文献扫描发现，尚无基准评测模型在多阶段任务中对进度报告的可靠性，且无法将"未报告"与"报告错误值"区分开来。

## 核心贡献（创新点）
1. **发现阶段依赖性报告可靠性**：定位了报告弱点随任务阶段变化的规律，包括中途下降（mid-task decline）和完成阶段错误两类模式，不同部署的弱点位置并不相同。
2. **提出Setting-dependent失败形式分析**：在τ²-bench中，错误报告通常指向已过去的阶段；在StageIF中，遗漏报告和用工具调用替代报告是下降的主因，揭示了两种评测设置暴露不同失败模式。
3. **构建StageIF测量工具与失败分类学**：受控测试床可在任务任意位置放置报告义务、冻结正确答案、独立评分四层失败（代替报告/遗漏/格式错误/错误值），使"报告为何失败"变得可测量。
4. **设计有界干预测试**：系统测试了值注入、提示提醒、阶段信息增强和推理模式切换，发现这些简单变更通常无法消除报告差距，且报告变化与任务进度脱钩。

## 方法详解
**评测框架与指标体系**：
- **τ²-bench增强**：在电信/零售对话基准上，要求每条面向客户的回复末尾附加生命周期阶段标签（NEEDS_INFO/READY/POST_OBS/COMPLETED），正确答案由环境状态机械派生，与模型回答独立。
- **StageIF受控测试床**：12个合成场景（6个日程安排+6个客户支持），每个场景产生5个检查点（4个报告义务激活，1个禁止报告），采用冻结历史+冻结Oracle的方式，分离"是否应报告"、"是否报告"、"报告是否正确"三个问题。
- **核心指标**：
  - $\hat{\theta}_z$（端到端依从性）：在阶段$z$的义务激活检查点，模型应在场、已报告且报告正确的比例。
  - $\hat{\phi}_z$（条件报告有效性）：仅在有工具调用的检查点上条件限制后的诊断指标。
  - $\hat{\omega}$（正确省略）：在义务非激活检查点上，模型正确不报告的比例。
  - $\hat{\mu}_t/\hat{\nu}_t$（错误完成）：声称COMPLETED但任务未完成的分享。

**失败分类优先级**：TRANSPORT > APP_MISS（说而未报）/ APP_DIVERGENCE（应说而调用工具）/ APP_FALSE_ALARM（义务非激活时报了）> MALFORMED > STATE_WRONG > CLEAN。

**干预实验设计**：
- Gold-injected：直接在上下文中注入真实阶段。
- Static-value：替换为恒定值。
- Trailing reminder：在冻结历史末尾追加提醒。
- 责任×可执行性分解：2×2×2因子设计，分别改变工具可用性、归属方、反馈线索。

## 实验与结果
**数据集**：
- τ²-bench（电信/零售对话，11个部署）
- StageIF（12个合成场景×20次重复×9个部署=50,400检查点）

**主要结果**：
- **τ²-bench表现**：gpt-4.1/gpt-5.5在action前检查点正确率90.6–99.4%，完成后87.3–88.9%，但mid-task仅5.8–11.5%；最旧型号到最新型号（gpt-5.6-sol→gpt-6-astra）mid-task从28.6%提升至100%，但completion从40.3%降至48.1%。
- **StageIF baseline arm（Table 2）**：所有部署均呈现"mid-task下降→完成恢复"模式，非终态差Δ显著（除gpt-5.5外），范围29.4–89.3点，最极端部署qwen3.5-35b-a3b中间8.2%、终端97.4%。
- **失败模式分解（Figure 5/6）**：mid-task下降主要由"遗漏报告"和"工具调用替代报告"（divergence）驱动，而非错误值——错误值错误在StageIF中仅达13.6点，而τ²-bench中占主导。
- **干预效果**：
  - Gold-injected静态值：仅缩小最多1/6的差距（上置信限）。
  - Trailing reminder：最大增益+9.3点，但动作-bearing检查点的divergence几乎不变。
  - 责任×可执行性因子：工具撤回是唯一对所有部署非负的因子（+0.3–18.7点），但false completion从6.2%飙升至64.4%。
- **运营影响**：标记报告配置（marker gate）比无工具调用配置（no-tool-call）少完成13.0点任务（CI [+7.1, +19.4]），22.7%轨迹因缺少标记而终止，仅1.6%因过早完成声明终止。

**最强结果**：claude-opus-5在StageIF完成阶段达98.8%，但mid-task为54–60%；gpt-6-astra（envelope-stripped）mid-task达100%，但completion仅48.1%。

## 相关工作脉络
1. **指令遵循基准**（IFEval、Multi-IF、EvolIF等）：评估面向用户的响应约束，但义务始终激活，无法表达"某些轮次应报告、某些轮次禁止报告"的阶段依赖特征。
2. **结构化输出基准**（SchemaBench、StructEval等）：单轮固定schema，不涉及多轮任务中义务的动态激活/停用。
3. **进度自我估计**（Bishop et al., 2024; Ma et al., 2026; Park and Choi, 2026）：前者对人标注评分而非环境状态派生；后者在线进度提示反而损害任务性能；第三篇发现自评循环将停滞误判为进步。本文通过环境派生truth和阶段激活义务，将遗漏与错误值分离。
4. **过程/状态评估**（ToolSandbox、BFCL、ACEBench等）：评分动作和里程碑，不测模型向运行时发出的生命周期信号。
5. **前瞻性记忆**（PM-Bench、TriggerBench）：关注单响应延迟义务，本文扩展到多轮、阶段激活、机器消费的协议，并分解适用性/状态选择/实现三失败维度。
6. **Agent运行时终止机制**： survey显示17个框架中13/17依赖模型生成信号（B1/B2/B3类），本文的StageIF是对此类设计压力测试。

## 局限性与未来方向
1. **部署标识符非排名**：每个identifier命名模型+服务配置捆绑包，不同endpoint可能静默丢弃采样参数，数值不代表能力排序。
2. **行为层面结论**：所有发现均为行为层面的，不揭示模型内部如何表示进度（stage与对话深度共变，无法因果分离）。
3. **干预的非因果性**：有界干预仅识别总效应，bundle干预不能分解各组件效应。
4. **terminal检查点的幸存者偏差**：验证 rollout中terminal检查点由存活轨迹构成，不能推断rollout阶段的中间差距。
5. **未来方向**：探索memory增强、推理模式与报告可靠性的关系；研究模型是否具备内部进度表征；将StageIF扩展至更多领域和更长轨迹。

## 研究启发与可借鉴点
1. **冻结Oracle设计**：在评估前冻结正确答案和检查点归属，使"义务是否存在"、"答案是什么"、"模型回答是什么"三者独立可评分，是构建可审计Agent基准的通用范式。
2. **分层失败分类学**：将"未报告"、"格式错误"、"值错误"、"模式选择错误（应为言语而调用工具）"分离评分，比单一准确率更能定位问题根源，值得迁移至其他结构化输出评测。
3. **双设置互补验证**：τ²-bench展示自然轨迹中的问题，StageIF通过受控检查点分离各失败维度，形成"生态效度+诊断清晰度"的组合，可用于其他Agent能力评测。
4. **有界干预而非机制解释**：系统测试多种prompt工程干预但不宣称单一机制，保持结论的保守性和可复现性，为后续研究提供清晰的边界条件。
5. **与团队结合机会**：本研究的失败分类可与团队在Agent终止决策、结构化输出、长期任务跟踪等工作结合，例如将StageIF范式应用于多智能体协作中的状态同步评测。

## 关键术语表
**StageIF**：Lifecycle-stage Instrumentation Framework的缩写，一种受控测试床，在任务脚本的任意位置插入报告义务检查点，冻结正确答案后评估模型报告。

**Lost-mid-task pattern**：描述性术语，指模型在任务中途（action-bearing checkpoints）报告可靠性显著下降、完成后恢复的模式，不暗示普遍性或内在机制。

**End-to-end adherence ($\hat{\theta}_z$)**：核心评估指标，在阶段$z$的义务激活检查点上，模型正确履行交互模式、成功报告且报告值与truth一致的比例。

**Conditional report validity ($\hat{\phi}_z$)**：诊断指标，条件于检查点无助手工具调用时的报告有效性，用于分离模式选择失败与协议失败。

**APP_DIVERGENCE**：失败代码，指模型在报告义务激活时调用工具而非言语，属于模式选择失败而非协议失败。

**Gold-injected arm**：干预实验的一种，在上下文中直接告知模型真实阶段值，用于测试纯协议遵循是否为主要瓶颈。

**Runtime-owned gate vs Model-emitted gate**：前者由框架代码从结构化状态派生continue/stop决策（如LlamaIndex StopEvent），后者读取模型生成信号（如CAMEL marker、无工具调用即停止）。
