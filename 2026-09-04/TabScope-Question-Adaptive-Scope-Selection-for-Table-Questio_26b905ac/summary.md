# 论文速读：TabScope: Question-Adaptive Scope Selection for Table Question Answering

## 一句话总结
论文提出 **TabScope** 框架，通过问题自适应的表格范围选择，动态决定对每个表格问答（TableQA）问题使用**局部化子表推理**还是**完整表格推理**，从而缓解大语言模型（LLMs）随表格规模增大而出现的准确率下降问题。

## 研究问题与动机
1. **表格规模增大导致准确率下降**：LLMs在TableQA任务中，随着表格行数/列数增加，难以从噪声中定位支撑答案的关键行和列，准确率下降。
2. **现有方法未考虑问题类型差异**：现有表格分解或检索方法通常对所有问题采用固定的局部化策略，但不同问题（如查找类 vs 统计类）对表格上下文的需求不同。
3. **缺乏长表格基准与证据标注**：现有基准（如WikiTQ）表格较小且缺少对支撑子表的显式标注，难以直接评估分解质量与长表格推理能力。

## 核心贡献（创新点）
1. **银参考子表（Silver Reference Sub-tables）**：通过LLM直接预测并结合校验器修复，为WikiTQ测试集构建带有行/列标注的子表，用于直接评估分解质量。
2. **操作感知表格分解（Operation-aware Table Decomposition）**：不仅依赖词汇重叠，而是根据问题所需的推理操作（如过滤、比较、计数）选择行和列，并通过多采样聚合与子表细化提升稳定性。
3. **问题自适应范围选择（Question-Adaptive Scope Selection）**：根据预测的问题类型和表格大小，动态决定使用局部化推理还是完整表格推理，避免一刀切。
4. **长表格基准 SLQA**：从真实世界大表（Spider中token>4096的表）自动构建带人工复核的问答对，填补长表格TableQA评测空白。

## 方法详解
**框架流程**：输入（问题q, 表格T）→ 范围选择器 → 决定使用局部化或完整表格 → 若局部化则经过操作感知分解器生成细化子表T' → 答案模型生成答案。

1. **问题形式化**：将子表定义为原表的行子集R'与列子集C'，即T'=T[R', C']，目标不是最小化表格，而是为每个问题选择合适范围。
2. **范围选择器**：LLM分类器预测问题类型τ̂，结合固定策略π（基于离线验证集分析得到）决定作用类型z∈{local, full}。
3. **操作感知分解**：
   - **操作感知检索**：分别检索所需行和列，提示明确要求识别操作类型（lookup/filtering/comparison等）并保留支撑操作的证据。
   - **证据聚合**：对K=4次检索结果进行聚合，按行/列分组计算支持权重w(g)=Σexp(s(c))（s(c)为置信度，若无则基于频率投票），选取覆盖权重高且紧凑的行/列组合。
   - **子表评分**：Support(R',C')=√(RowScore·ColScore)，综合紧凑性得分S=Support/ρ^α（ρ为保留单元格比例，α∈[0.1,0.3]惩罚大子表）。
   - **子表细化**：默认一次细化迭代，验证器检查子表是否足够，不足则补充缺失行/列。
4. **答案生成**：使用链式思考（CoT）提示，在选定子表（或完整表）上生成最终答案。

## 实验与结果
**数据集**：
- **WikiTQ**：标准表格问答基准，含中小表格（平均662.6 token）。
- **SLQA**：自建长表格基准，所有表格>4096 token（平均9786.2 token）。
- **WTQ-SUBTAB**：银参考子表，用于评估分解质量。

**基线**：分解类（DATER、Chain-of-Table、TabSQLify、TableRAG、Table-Critic）与全表推理类（CoT、RoT）。

**主要结果**（Exact-match accuracy %）：
- **WikiTQ**：TABSCOPE平均82.2%（GPT-5-mini 83.3%，LLaMA-3.3-70B 81.1%），优于最强分解基线（DATER 73.4%）约8.8个百分点。
- **SLQA**：TABSCOPE平均68.1%，分解-only变体达67.1%，显著提升长表格场景性能。
- **分解质量**（WTQ-SUBTAB）：TABSCOPE在Cell F1（70.70）、Row F1（82.78）、Column F1（86.95）上均优于所有基线。

**类型分析**：查找、排序、局部推理、计数差异类问题适合局部化；一般计数、频率计数（大表时）、比较类问题更适合全表推理。

## 相关工作脉络
1. **证据定位与检索**：DATER、TableRAG等利用LLM检索相关行/列或schema，但未考虑问题类型与操作需求；TabScope引入操作感知与范围自适应。
2. **程序引导分解**：Chain-of-Table、TabSQLify等通过迭代变换或生成SQL构造中间表；TabScope不依赖完整程序链，仅在必要时分解。
3. **证据监督与长表格评估**：现有基准缺乏子表标注且表格规模有限；本文提供银参考子表与SLQA长表格基准，推动可评估的长表格研究。
4. **现有方法局限**：多数方法固定采用分解或全表策略，未探索“何时局部化”的问题依赖性。

## 局限性与未来方向
1. **评估范围**：仅在英文TableQA基准与两个LLM（GPT-5-mini、LLaMA-3.3-70B）上验证，跨领域、语言与模型家族的一般性需进一步测试。
2. **策略灵活性**：当前范围选择策略基于预定义问题类型分类法，未来可探索更灵活的动态路由机制。
3. **长表格覆盖**：SLQA仅包含超过4096 token的表格，中等规模表格的鲁棒性未深入探讨。

## 研究启发与可借鉴点
1. **问题自适应推理范式**：将“何时局部化”作为独立决策步骤，而非固定预处理，对检索增强生成（RAG）等多文档任务有借鉴意义。
2. **操作感知的证据选择**：结合推理操作类型指导行/列选择，比纯语义匹配更精准；可迁移至复杂查询分解、代码生成等需要结构化证据的场景。
3. **银参考子表构建方法**：直接生成+校验器修复的两阶段策略，为其他需要中间证据标注的评测集构建提供可行路径。
4. **长表格基准构建Pipeline**：从真实数据提取大表、多证据范围生成问答对、人工复核的质量控制流程，可直接复用于其他领域长上下文数据集构建。

## 关键术语表
- **TabScope**：本文提出的表格问答框架，根据问题类型动态选择局部化子表或完整表格推理。
- **Silver Reference Sub-tables**：通过LLM预测并结合校验器修复构建的参考子表，用于评估分解方法的行/列选择质量。
- **Operation-Aware Decomposition**：基于问题所需推理操作（查找、过滤、比较等）选择证据行/列的分解方法。
- **Scope Selection Policy**：根据问题类型和表格大小决定使用局部化或全表推理的固定映射规则。
- **SLQA**：从真实长表格自动构建的问答基准，所有表格序列化token数超过4096。
- **WTQ-SUBTAB**：基于WikiTQ测试集构建的银参考子表数据集，包含4344个问答对的标注子表。
- **Evidence Aggregation**：对多次检索结果按行/列分组，基于置信度或频率加权聚合以提升选择稳定性。
- **Sub-table Refinement**：对初步生成的子表进行一次验证与补充迭代，确保证据充分性。
